# Experiment 06: Fault Injection

## Requirement

Demonstrate Istio fault injection using a 3-second delay, a 100% HTTP 503 abort, and a 25% HTTP 503 abort.

## Objective

Verify that the service mesh can introduce controlled failures without modifying Payment Service application code.

## Environment and Configuration

| Parameter | Value |
|---|---|
| Kubernetes context | kind-istio-part3 |
| Namespace | istio-part3-sidecar |
| Traffic management | Istio VirtualService |
| Target | Payment Service |
| Delay policy | manifests/sidecar/20-fault-delay.yaml |
| Abort policy | manifests/sidecar/21-fault-abort.yaml |
| Percentage policy | manifests/sidecar/22-fault-percentage.yaml |

## Test Procedure

1. Apply the 3-second delay configuration and send 3 requests.
2. Record client latency and Payment Service request counts.
3. Apply the 100% HTTP 503 abort configuration and send 10 requests.
4. Verify that the failures occurred before requests reached Payment.
5. Apply the 25% HTTP 503 abort configuration and send 80 requests.
6. Compare client errors with backend request counts.

Execution command:

    bash scripts/12-run-fault-injection.sh

## Results

| Scenario | Requests | HTTP 200 | HTTP 502 | Error rate | Payment requests |
|---|---:|---:|---:|---:|---:|
| 3-second delay | 3 | 3 | 0 | 0% | 3 |
| 100% abort | 10 | 0 | 10 | 100% | 0 |
| 25% abort | 80 | 65 | 15 | 18.75% | 65 |

## Scenario A: Three-Second Delay

| Metric | Result |
|---|---:|
| Average latency | 3024.323 ms |
| p50 latency | 3024.434 ms |
| p95 latency | 3024.541 ms |
| p99 latency | 3024.551 ms |
| Successful requests | 3 |
| Payment requests | 3 |

All three requests succeeded after approximately three seconds.

This confirms that Istio introduced latency while still forwarding the requests to Payment Service.

Because the sample contains only three requests, the latency percentiles are descriptive rather than statistically representative.

## Scenario B: 100% HTTP 503 Abort

| Metric | Result |
|---|---:|
| Requests | 10 |
| Client HTTP 502 | 10 |
| Client error rate | 100% |
| Downstream status observed by Order | HTTP 503 |
| Payment requests | 0 |

All ten requests failed.

Order Service observed HTTP 503 from its downstream call and returned HTTP 502 to the client.

Payment Service received zero requests, confirming that the fault was injected before the backend application.

## Scenario C: 25% HTTP 503 Abort

| Metric | Result |
|---|---:|
| Requests | 80 |
| Successful requests | 65 |
| Failed requests | 15 |
| Observed error rate | 18.75% |
| Configured abort percentage | 25% |
| Payment requests | 65 |
| Average latency | 34.922 ms |
| p95 latency | 50.393 ms |

The configured abort percentage is probabilistic.

The observed result of 15 failures out of 80 requests is consistent with a probabilistic 25% abort configuration, although the sample does not establish the exact long-run failure probability.

The 65 backend requests match the 65 successful client requests. This supports the conclusion that the 15 failures were generated by the proxy before Payment Service.

## Initial Execution and Correction

The initial execution did not activate the 3-second delay or the 100% abort as expected.

| Scenario | Initial observation |
|---|---|
| 3-second delay | Average latency 20.362 ms |
| 100% abort | 10 successful responses |
| 25% abort | 16 failures out of 80 requests |

The test script applied VirtualService resources immediately before sending requests.

A 5-second stabilization period was added after applying each configuration.

The repeated test produced the expected delay and abort behavior.

The results support configuration propagation timing as a possible explanation for the first discrepancy. However, the Envoy configuration was not inspected directly, so the exact cause remains unconfirmed.

## Analysis

Fault injection is useful for testing system behavior under controlled failures without deliberately breaking the backend application.

The delay experiment confirmed an increase in response time of approximately three seconds.

The 100% abort experiment showed that proxy-generated failures can prevent requests from reaching Payment Service.

The percentage-based experiment showed how a subset of requests can be rejected while the remaining traffic continues normally.

Client-facing HTTP status codes may differ from injected downstream codes because Order Service transforms dependency errors.

Backend counters provide important independent evidence of where failures occurred.

## Conclusion

All three fault injection scenarios were demonstrated successfully after stabilizing the proxy configuration.

The experiments confirmed delay injection, complete request aborts, and probabilistic aborts.

The results also demonstrate why client status codes and backend request counts should be analyzed together.
